# BAA — Build Any App

[실행 규칙](EXECUTION.md)을 읽는다. BAMA·BAWA 기반 절차와 모바일 전문 절차가 이 플러그인에 포함되어 있다.
직접 `/baa`로 호출했으면 호출 진입점은 `baa`다. `/baa-apple`, `/baa-android`, `/baa-windows`가 이 문서를 읽도록 연결했으면 그 진입점과 허용 범위를 그대로 유지한다.

## 1. 대상 판정

[라우팅 목록](routing.json)의 `entrypoints`가 진입점별 허용 플랫폼이다.
`baa`는 macOS·iOS·iPadOS·Android·Windows, `baa-apple`은 macOS·iOS·iPadOS,
`baa-android`는 Android, `baa-windows`는 Windows로 범위를 제한한다.
진입점은 이번 호출의 범위다. 다음에 사용자가 다른 명령으로 호출하면 그 새 진입점을 적용하며 이전 직접 호출 범위를 대화 전체에 고정하지 않는다.

다음 근거를 순서대로 읽고 이번 작업의 구체 대상을 결정한다.

1. 현재 요청에서 작업 대상으로 명시한 플랫폼. iPhone은 iOS, iPad는 iPadOS, Mac은 macOS로 정규화한다. 참고 앱이나 비교 대상으로 언급한 플랫폼을 작업 대상으로 추가하지 않는다.
2. 같은 작업에서 이미 확정한 대상. 현재 요청이 대상을 바꾸거나 다른 파일·모듈을 가리키면 과거 결정을 그대로 적용하지 않는다.
3. 지정 파일·모듈의 실제 소속 타깃. Xcode의 지원 플랫폼·device family·scheme, Gradle source set/모듈, Windows 프로젝트의 실제 타깃과 호출부를 확인한다.
4. 요청 범위와 관련된 프로젝트의 실제 지원 타깃. 후보가 하나면 선택하고, 여러 개면 임의로 전체를 고르지 않는다.

후보는 진입점 허용 범위 안이어야 한다. `/baa-android`와 Windows 작업처럼 명령·본문이 충돌하거나,
지정 파일이 허용 범위 밖이면 수정 전에 충돌을 설명하고 대상을 확인한다. 다른 플랫폼으로 자동 전달하지 않는다.
본문에 별도 모순이 없으면 Android/Windows 직접 호출 자체로 대상이 확정된다. 기존 프로젝트에 해당 타깃이 없으면 다른 플랫폼을 선택하지 않고 신규 지원 추가인지 범위를 확인한다.

확정 근거가 부족하면 후보를 제시하고 어떤 플랫폼을 작업할지 한 번 묻는다. 응답 전에는 읽기 전용 조사만 한다.
`/baa-apple`은 Apple 계열을 선택하는 명령이지 세 플랫폼 전체를 자동 선택하는 명령이 아니다.
Swift·Kotlin·확장자·호스트 OS만으로 판단하지 않는다. 공유 Swift 파일이 macOS·iOS·iPadOS에 포함되면 후보가 여러 개다.
기존 프로젝트의 `전체`는 진입점 범위 안에서 확인된 지원 타깃 전체, 신규 앱의 `전체`는 진입점의 허용 플랫폼 전체다.
없는 타깃을 요청 없이 추가하지 않는다. iOS/iPadOS가 소스를 공유해도 대상 기기와 검증은 구분한다.

선택한 플랫폼과 근거를 짧게 알리고 목적을 신규 앱 / 기능 추가·수정 / 디자인 개선 / 조사·검토 / 빌드·검증에서 판단한다.
분명한 플랫폼이나 목적은 다시 묻지 않는다.

## 2. 플랫폼 담당자와 작업 단계 연결

실행 패키지 루트는 이 SKILL.md가 있는 실제 디렉터리다. 심볼릭 링크로 호출되면 먼저 실제 경로를 확인한다(예: `Path(<SKILL.md 경로>).resolve().parent`). 플러그인 설치와 skills CLI 설치 모두 이 폴더 안의 절차·도구·템플릿을 사용한다. 현재 설치본 기준으로 계산하고 원본의 절대 경로를 넣지 않는다.
각 대상의 `router` 역할을 먼저 조회해 플랫폼별 단계 선택 지침을 읽는다. 이미 읽은 플랫폼 라우터로 재귀 진입하지 않는다.

```sh
python3 <실행 패키지 루트>/scripts/resolve.py --entrypoint <호출 진입점> --platform <대상> --step router
python3 <실행 패키지 루트>/scripts/resolve.py --entrypoint <호출 진입점> --platform <대상> --step <필요한 역할>
```

`routing.json`은 단계와 문서의 단일 연결 표다. resolver가 반환한 `path`의 PROCEDURE.md와 필요한 `references`만 읽어 수행한다.
내부 이름을 Skill 도구나 슬래시 명령으로 호출하지 않는다. 공개 진입점 네 개는 같은 실행 규칙을 사용한다.
macOS는 BAMA 기반, Windows는 BAWA 기반, iOS·iPadOS·Android는 해당 전문 절차를 사용한다.

- 신규 앱: research → clone(선택) → app-brief → user-stories → scaffold → native-design + design-system + app-icon → improve-loop.
- 기존 기능: 해당 요구와 기존 작업 목록 확인 → 필요한 ux-design → code/os-integrations → build-and-verify + test.
- 디자인만: 필요한 ux-design → native-design → design-system/design-kit/design-from-app/layout-grid 중 필요한 역할 → build-and-verify와 변경 영향에 필요한 test.
- 성능: performance → 확인된 원인 수정 → 대상 검사. 구조 개선은 improve-architecture.
- 검토만: 해당 역할을 읽고 관찰·제안만 반환한다. 생성·수정·설치·커밋을 시작하지 않는다.
- 배포 요청: 해당 플랫폼의 distribute 또는 실제 프로젝트 릴리즈 절차. 요청한 외부 게시 범위를 지킨다.

기존 앱에서 전체 기획을 다시 하거나 모든 문서를 미리 읽지 않는다. 원본 템플릿에 맞추려고 기존 기술을 전환하지 않는다.

## 3. 공통 결정과 플랫폼별 배정

공통 동작·용어·데이터 계약·완료 기준은 한 번 정한다. 소스·테스트·리소스를 확인해 플랫폼별 파일 소유권과 공유 파일 담당자 한 명을 정한다.
공통 절차를 사용하더라도 직접 호출의 허용 플랫폼 밖 기능·UI를 추가하지 않는다. 공유 파일은 선택 대상에 필요한 최소 변경을 하고 비선택 타깃에 대한 영향도 보고한다.

독립 작업은 사용 가능한 서브에이전트 도구로 플랫폼별 담당자에게 병렬 배정한다.
iOS/iPadOS/macOS가 같은 파일을 수정하면 한 Apple 담당자로 묶거나 선행 공유 변경을 통합한다. 소스가 독립적일 때만 나눈다.
슬롯 한도 내에서 실행하고 에이전트 도구가 없으면 순차 수행임을 알린다. 하위 담당자에게 팀을 다시 만들게 하지 않는다.

인계에는 호출 진입점·허용 플랫폼·선택 대상과 근거·목적·현재 단계·프로젝트와 실제 기술·소유 파일·제외 범위·공유 계약·완료 기준·
resolver가 반환한 절차 경로·검증 환경을 포함한다. 대상과 기획을 다시 선택하지 않도록 한다.
“다른 담당자가 함께 수정 중이므로 타인의 변경을 되돌리지 말고, 소유 범위 밖 변경은 제안으로 반환하세요”라고 명시한다.
공통 문서의 상태 갱신과 공유 변경 통합은 중앙 조율자가 맡는다.

## 4. 통합과 종료

결과의 소스 상태·대상·검증 환경·증거·미검증을 확인하고 공유 변경을 통합한다.
다른 담당자 변경으로 검사 근거가 달라졌으면 영향받는 검사만 다시 수행한다.
코드 작성, 빌드, UI 실행과 실기기 검증을 구분해 플랫폼별로 보고한다. 막힌 플랫폼이 있어도 독립 작업은 계속한다.
검증이 남으면 전체 완료로 표현하지 않고 실제 근거와 재개 조건을 남긴다.
