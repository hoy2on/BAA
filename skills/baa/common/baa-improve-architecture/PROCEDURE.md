# Improve architecture

[공통 실행 규칙](../../EXECUTION.md)을 먼저 읽는다. BAA가 전달한 선택 플랫폼, 작업 목적, 현재 단계, 파일 소유권과 완료 기준을 유지한다. 플랫폼을 다시 선택하거나 전체 기획을 반복하지 않는다.

후속 스킬은 실행 패키지 루트에서 `python3 scripts/resolve.py --entrypoint <호출 진입점> --platform <선택 플랫폼> --step <단계>`로 조회한다. 반환된 이름과 문서 경로를 사용하며 원본 BAMA·BAWA의 짧은 이름이나 외부 설치 경로를 추정하지 않는다. 반환된 path의 PROCEDURE.md를 읽어 수행한다. 내부 이름을 Skill 도구나 슬래시 명령으로 호출하지 않는다. resolver 결과에 `references`가 있으면 선택 플랫폼의 원본 부속자료 중 현재 작업에 필요한 파일만 읽는다.

공유 문서의 최종 편집자는 BAA 조율자 한 명이다. 플랫폼 담당자는 공유 BRIEF/STORIES/GLOSSARY/연구·검토 문서를 동시에 수정하지 않고 변경 제안과 근거를 조율자에게 반환한다. 단독 실행에서는 현재 담당자가 그 역할을 맡는다.

BAMA·BAWA의 survey → propose → refactor → record 순서를 공유한다. 목표는 현재 변경 비용을 줄이는 것이며 플랫폼 기술을 통일하거나 새 계층을 늘리는 것이 아니다.

## 1. Survey

먼저 코드를 바꾸지 않는다. 존재하는 프로젝트 지침, ARCHITECTURE, ADR, FIXLOG와 관련 소스를 읽는다. git 변경 이력, 큰 파일, 반복 버그, 많은 호출부, UI 상태의 잦은 갱신, main/UI thread에서의 느린 작업, 테스트하기 어려운 의존성으로 실제 hot spot을 찾는다. 파일 크기는 조사 신호이며 숫자만으로 분할하지 않는다.

타깃·프로젝트와 의존 방향, 도메인 규칙과 UI·I/O 경계, 스레드·lifecycle 소유권을 그린다. 플랫폼의 `code`, `performance`, `test` 스킬을 조회해 실제 언어·프레임워크의 제약을 확인한다. 다음을 조사한다.

- 여러 화면을 모두 소유하는 상태 객체와 불필요하게 넓은 갱신 범위.
- 호출을 전달만 하는 wrapper와 한 구현뿐인 추측성 interface.
- UI 이벤트에 묶인 순수 로직, 느린 작업과 동기 대기.
- 다른 모듈 내부에 의존하는 코드와 서로 달라진 복제 구현.
- 테스트 접근을 위해 공개된 내부 경로와 production 데이터에 접근하는 test mode.
- 기능과 멀리 떨어진 관련 화면·설정·테스트 및 공유 파일 소유권 충돌.

삭제 검사를 한다. 모듈을 없앴을 때 복잡성이 한 곳에 모이면 단순화 후보이고, 모든 호출부로 퍼지면 그 경계가 필요한 근거다. 언어별 특정 API와 템플릿의 이름을 모든 프로젝트 전제로 삼지 않는다.

## 2. Propose

조율자는 기존 검토 문서 또는 `docs/architecture-review-<날짜>.md`에 후보별로 파일, 관찰 신호, 현재 어려운 변경의 예, 최소 제안, 호출부 영향, 동작 동일성 증명과 실행 순서를 적는다. 등급은 Strong / Worth exploring / Speculative로 구분하고 최우선 제안과 검토했지만 추천하지 않은 대안을 남긴다. 수정할 근거가 없다는 결론도 유효하다.

요청이 검토뿐이면 제안으로 끝낸다. 이미 승인된 리팩터링 범위는 반복 승인 없이 진행하되, 미승인 기능 확대·데이터 변경은 실행하지 않는다. improve-loop의 milestone 점검에서는 현재 기능에 필요한 Strong 제안만 기존 권한 안에서 적용하고 나머지는 제안으로 남긴다.

## 3. Refactor and prove

변경 전 관련 unit/integration/self-test, 화면·상호작용, golden output, 기존 데이터·설정 로딩, 필요한 성능 수치를 확보한다. 해당 플랫폼의 `test`와 `build-and-verify`로 확인하고 실제 도구가 없는 항목은 대기로 둔다.

한 번에 하나의 구조 변경을 하고 기능 변경을 섞지 않는다. 기존 경계·타입을 우선하며 새 추상화는 실제 호출부나 검증상의 이익이 있을 때만 만든다. 새 구현으로 호출부를 옮길 때 오류 처리·검증·호환성을 보존하고 안전하게 낡은 경로를 제거한다. 임시 호환 flag나 이중 경로를 관례적으로 추가하지 않는다.

공유 API·데이터 계약과 프로젝트 구성이 바뀌면 담당자 한 명이 반영하고 영향을 받는 플랫폼의 회귀를 확인한다. 다른 담당자의 변경을 되돌리지 않는다. 변경된 범위에 필요한 검사로 이전 증거와 비교하고 동작 차이가 있으면 원인을 수정한다. 커밋은 현재 권한과 프로젝트 절차에 따르며 관계없는 파일을 stage하지 않는다.

## 4. Record

실제 구조가 바뀌었으면 기존 ARCHITECTURE의 경계와 의존 방향을 갱신한다. 되돌리기 어려운 결정과 실제 trade-off가 있을 때만 ADR을 추가한다. 버그를 발견·수정했다면 FIXLOG에 증상·원인·수정·재발 방지 Rule을 남긴다. 작은 변경에 새 문서 묶음을 강제하지 않는다.

완료 기준: 검토 근거와 선택이 명확하고, 승인된 변경의 호출부·호환성·관련 검사가 확인됐으며, 검토만 한 범위와 실행·검증한 범위가 구분되어 있다.
